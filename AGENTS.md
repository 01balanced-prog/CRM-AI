# Balance CRM

Внутренняя CRM для менеджера продаж компании Balance (Грозный). Продаём внедрение ИИ-агентов
для приёма заказов в WhatsApp. Пользуется один человек, с телефона, стоя, во время обзвона.

Отвечай и комментируй код по-русски. Весь интерфейс на русском.

## Стек и его границы

Один файл `index.html`: HTML, CSS и JS вместе. Vanilla JS, без фреймворков.
База — Supabase (Postgres + PostgREST), обращение напрямую через `fetch`, без клиентских библиотек.
Хостинг — GitHub Pages / Netlify, публикация перетаскиванием файла.

**Сборки нет и не будет.** Ни npm, ни Vite, ни бандлера, ни TypeScript, ни зависимостей из CDN.
В команде нет разработчика: владелец публикует изменения, перетаскивая файл на хостинг.
Любой шаг сборки убивает этот способ работы.

**Не разбивай `index.html` на модули.** Один файл — осознанное решение, а не недоделка.

**Не предлагай переписать на React/Vue/Next.** Это не улучшение, это потеря возможности
поддерживать проект.

## Что выглядит ошибкой, но ею не является

**Ключ Supabase лежит в открытом виде в `index.html`.** Так и задумано: это publishable key,
он безопасен для публикации. Доступ режут политики RLS, регистрация в проекте закрыта.
Не выноси его в переменные окружения — сборки нет, подставить их некому.

**`.sql` файлы не применяются автоматически.** Владелец вставляет их вручную в SQL Editor.
Никогда не создавай папку `supabase/` — интеграция Supabase с GitHub подхватит
`supabase/migrations` и начнёт применять миграции сама. SQL держим в `db/`.

**Токен сессии в localStorage.** Обычная схема для SPA без бэкенда.

## Правила работы с базой

`db/01_schema.sql` и `db/02_seed.sql` **никогда не запускаются повторно.** Они отработали.

Любое изменение схемы — новый файл `db/NN_описание.sql`, только дописывающий.
Существующие файлы не редактируются.

**`create table if not exists` не добавит колонку в существующую таблицу.** Пропустит блок
целиком и вернёт `Success` — молча, без предупреждения. Колонки добавляй только через
`alter table ... add column if not exists`.

**Представления пересобираются цепочкой.** Зависимость: `v_stats` → `v_today` → `v_leads`.
Сносить в этом порядке, создавать в обратном. `create or replace view` не годится,
когда меняется набор колонок — Postgres откажет с `cannot drop columns from view`.

Каждое представление создаётся **только** с `with (security_invoker = true)`. Без этого оно
выполняется с правами владельца и обходит RLS: посторонний увидит все данные через вьюху,
хотя из таблиц напрямую не увидит ничего.

**Внутри представлений не вызывай `auth.uid()` напрямую** — упрётся в права на схему `auth`.
Только `current_profile_id()` (security definer).

После пересоздания представлений **обязательно** повтори
`grant select on v_leads, v_today, v_stats to authenticated;` — права теряются вместе со старым объектом.

В настройках проекта выключен автоэкспорт новых таблиц. Каждая новая таблица требует явного
`grant` для роли `authenticated`, иначе PostgREST вернёт `permission denied`.

Доступ даёт не авторизация, а наличие строки в `profiles` (`is_staff()`). Так задумано:
ключ публичный, поэтому одного входа мало.

## Бизнес-правила, вшитые в базу

Не ослабляй их ради удобства. Каждое стоит за конкретной ошибкой, которую они предотвращают.

- Суммы внедрения и подписки **вычисляются из таблицы `tariffs`** триггером, а не вводятся руками.
  Менеджер не может дать скидку — база вернёт ошибку. Ручной прайс только у админа
  через `custom_pricing`.
- Этапы оплаты 30/30/40 считаются от `setup_amount` в представлении. Третий этап —
  вычитанием первых двух, чтобы сумма трёх всегда сходилась с итогом до рубля.
- **Журнал касаний неизменяем.** Нет политик update и delete, плюс триггер. Не добавляй их.
- Статус вне `new/won/lost` не сохраняется без `next_action_at`. Отказ не сохраняется без причины.
- Пять недозвонов подряд закрывают лид автоматически с причиной `unreachable`.
- Смена статуса и отметка оплаты сами пишутся в журнал триггером.
- Один ЛПР на компанию, одна открытая сделка на компанию — уникальные частичные индексы.

## Как проверять изменения

Синтаксис JS (обязательно после каждой правки `index.html`):

```bash
node -e "const h=require('fs').readFileSync('index.html','utf8');
new Function(h.slice(h.lastIndexOf('<script>')+8,h.lastIndexOf('</script>')));console.log('ок')"
```

Интерфейс — Playwright с подменой сети. Реальный Supabase из песочницы недоступен, поэтому
перехватывай `**/*.supabase.co/**` и отдавай заготовленный JSON. Проверяй на вьюпорте 390×844.
Смотри на скриншоты: половина ошибок в этом проекте была не в логике, а в том, что кнопка
уезжала под сгиб экрана.

Миграции — на локальном Postgres 16, прогоняя **всю цепочку с нуля** и каждый файл **дважды**
(они обязаны быть идемпотентными). Роль `authenticated` создавай **до** `01_schema.sql`,
иначе гранты не применятся и тест соврёт.

Проверяй поведение отдельно от лица трёх ролей: админ, менеджер, посторонний с аккаунтом,
но без строки в `profiles` (должен видеть нули во всех таблицах и представлениях).

## При изменении index.html

Подними номер версии кэша в `sw.js` (`const V = 'balance-crm-vN'`). Иначе service worker
отдаст пользователю старую версию, и правка «не приедет».

## Стиль интерфейса

Токены в `:root`. Фон `#080808`, акцент `#00E676` — фирменные цвета, не менять.
Цифры, телефоны и суммы — моноширинным шрифтом (`--mono`), так они читаются столбиком.
Минимальная зона нажатия 48px. Верстай под большой палец: главное действие ближе к низу экрана.
Акцентным цветом красится только основное действие, не всё подряд.

Никаких внешних шрифтов и картинок: приложение должно открываться при плохой связи.

## Терминология

В текстах для клиентов Balance — всегда «Агент», никогда «бот».
Внутри CRM: «лид», «касание», «ЛПР», «этап оплаты», «ответственный».
