# Balance CRM

Внутренняя CRM для отдела продаж Balance. Один менеджер ведёт обзвон заведений общепита
в Грозном с телефона: список на сегодня, звонок в один тап, запись результата, воронка.

Устанавливается на телефон как приложение.

## Как это устроено

Один файл `index.html` — вся CRM: разметка, стили, логика. Vanilla JS, без фреймворков
и без сборки. Обращается напрямую к Supabase по HTTPS, промежуточного сервера нет.

Права разграничены на уровне базы: политики RLS, триггеры и ограничения. Приложение их
не проверяет и не может обойти — оно просто интерфейс.

Публикация: файл кладётся на статический хостинг. Ни установки, ни компиляции, ни CI.

## Что в репозитории

| | |
|---|---|
| `index.html` | вся CRM |
| `sw.js` | service worker, кэш оболочки |
| `manifest.json`, `icon-*.png` | установка на домашний экран |
| `db/*.sql` | схема и миграции по порядку номеров |
| `AGENTS.md`, `CLAUDE.md` | инструкции для ИИ-агента, там же правила базы |

Папку `supabase/` создавать нельзя: интеграция Supabase с GitHub подхватит из неё миграции
и начнёт применять их сама. SQL живёт в `db/`.

## Опубликовать изменение

1. Заменить файл в репозитории: Add file → Upload files → Commit changes.
2. Если менялся `index.html` — поднять версию кэша в `sw.js`:
   `const V = 'balance-crm-vN'`. Без этого телефон продолжит показывать старую версию.
3. Дождаться зелёной галочки у `pages-build-deployment` во вкладке Actions, около минуты.
4. На телефоне закрыть приложение через переключатель задач и открыть заново.

Репозиторий должен оставаться публичным: на бесплатном плане GitHub Pages для приватных
не работает. Это безопасно — ключ в файле публичный по замыслу, доступ режут политики базы.

## Применить миграцию

Supabase → SQL Editor → новая вкладка → вставить файл целиком → Run.

Порядок строгий, по номерам. Каждый файл заканчивается контрольным запросом — сверить,
что числа сошлись, прежде чем запускать следующий.

`01_schema.sql` и `02_seed.sql` больше не запускаются никогда. Они отработали.

Изменения схемы — только новым файлом `db/NN_описание.sql`, дописывающим. Существующие
файлы не редактируются: `create table if not exists` пропустит таблицу целиком и молча
вернёт «Success», не добавив ни одной колонки.

## Доступы

Две роли. **Менеджер**: ведёт лидов, пишет касания, меняет статусы, выбирает тариф,
отмечает оплату. **Админ**: то же плюс удаление, ручные цены, импорт, выгрузка,
переназначение ответственных, управление пользователями.

Журнал касаний неизменяем для обеих ролей.

Новый сотрудник заводится в два шага. Сначала Authentication → Users → Add user,
обязательно с включённым Auto Confirm. Затем в SQL Editor:

```sql
insert into profiles (id, name, role)
select id, 'Имя', 'manager' from auth.users where email = 'почта@пример.ru';
```

Без строки в `profiles` человек войдёт, но не увидит ничего. Так и задумано: ключ публичный,
поэтому одной авторизации недостаточно.

## Если база потеряна

Создать новый проект в Supabase (регион Frankfurt), в блоке Security выключить
«Automatically expose new tables» и включить «Enable automatic RLS». Затем:

1. Выполнить `db/*.sql` по порядку номеров, все шесть.
2. Authentication → Sign In / Providers → Email → выключить регистрацию.
3. Authentication → Users → завести людей с включённым Auto Confirm,
   затем выдать им доступ запросом из раздела «Доступы» выше.
4. Settings → API Keys → взять publishable key, Settings → Data API → взять Project URL.
   Вписать оба в начало блока `<script>` в `index.html`.

## Ограничения бесплатного плана

Проект Supabase встаёт на паузу после 7 дней без обращений к базе — снимается одной кнопкой
в панели, данные не теряются. При ежедневной работе не срабатывает.

Бэкапов на бесплатном плане нет. Раз в месяц: «Ещё» → «Выгрузить всё в Excel».
