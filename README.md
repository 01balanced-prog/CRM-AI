# Balance CRM — шаг 1: база данных

Всё ниже делается в браузере. Занимает минут 20, программист не нужен.

## 1. Создать проект

1. [supabase.com](https://supabase.com) → Sign up → **New project**
2. Name: `balance-crm`
3. Database Password — сгенерировать и **сохранить в менеджер паролей**. Второй раз его не покажут.
4. Region: раскрыть **Europe** и выбрать **Frankfurt (eu-central-1)** — ближайший к Грозному по задержке
5. Блок **Security**:
   - Enable Data API — **включено** (это и есть прямой доступ из приложения)
   - Automatically expose new tables — **выключено**
   - Enable automatic RLS — **включено**
6. Plan: Free. Лимитов хватит с большим запасом: 500 МБ базы — это порядка 200 000 лидов.

Создание занимает 2–3 минуты.

## 2. Применить схему

**SQL Editor** (иконка слева) → **New query** → вставить целиком содержимое `01_schema.sql` → **Run**.

Ожидаемый результат: `Success. No rows returned`. Строки с `NOTICE ... does not exist, skipping` — это норма, файл рассчитан на повторные запуски.

## 3. Импортировать лиды

Новый запрос → вставить `02_seed.sql` → **Run**.

Последний запрос вернёт таблицу. Должно быть ровно:

| companies | contacts | leads |
|---|---|---|
| 26 | 28 | 26 |

28 контактов при 26 компаниях — потому что у MORE SUSHI из заметки вытащен второй номер, и у одной компании нашёлся дополнительный.

## 4. Создать пользователей

**Authentication** → **Users** → **Add user** → *Create new user*. Включить **Auto Confirm User**.

Создать двоих:
- твой email, пароль
- email менеджера, пароль

Затем **SQL Editor**, подставив реальные адреса:

```sql
insert into profiles (id, name, role)
select id, 'Юсуф', 'admin' from auth.users where email = 'ТВОЙ_EMAIL';

insert into profiles (id, name, role)
select id, 'ИМЯ_МЕНЕДЖЕРА', 'manager' from auth.users where email = 'EMAIL_МЕНЕДЖЕРА';
```

Проверка: `select name, role from profiles;` — должно быть две строки.

## 5. Закрыть регистрацию

**Authentication** → **Sign In / Providers** → **Email** → выключить **Allow new users to sign up** → Save.

Без этого любой желающий заведёт себе аккаунт. Схема его всё равно ничего не покажет (см. ниже), но лишняя дверь не нужна.

## 6. Забрать два значения

**Settings** → **API Keys**.

Нужен **Publishable key** — начинается с `sb_publishable_`. Если его нет, а есть только кнопка **Create new API keys** — нажми её, ключ создастся, старые не сломаются.

На вкладке **Legacy API Keys** лежит `anon` key — длинная строка на `eyJ`. Это то же самое по смыслу, но старый формат: Supabase объявил, что легаси-ключи будут отключены к концу 2026 года. Поэтому берём `sb_publishable_`, чтобы не переделывать через полгода.

Второе значение — **Project URL**, вида `https://xxxxxxxx.supabase.co`. Лежит в **Settings** → **Data API**.

Прислать мне: Project URL и Publishable key.

Ключ `sb_secret_` (и легаси `service_role`) не показывать никому и нигде не публиковать — он обходит все политики доступа.

## 7. Выложить на GitHub Pages

Делается после того, как я отдам `index.html`.

1. [github.com](https://github.com) → **New repository** → имя `balance-crm` → **Public**
2. **Add file** → **Upload files** → перетащить `index.html`, `manifest.json`, `sw.js` → **Commit changes**
3. **Settings** → **Pages** → Source: **Deploy from a branch** → Branch: `main`, папка `/ (root)` → **Save**
4. Через минуту адрес: `https://ТВОЙ_ЛОГИН.github.io/balance-crm/`

Репозиторий обязательно публичный: на бесплатном плане GitHub Pages для приватных репозиториев не работает. HTTPS включается сам, без него приложение не установится на телефон.

Обновление в дальнейшем: **Add file** → **Upload files** → тот же `index.html` → Commit. Через минуту у менеджера новая версия.

## Что уже заложено в базу

**Деньги не вводятся руками.** Менеджер выбирает тариф — суммы подставляются из сетки (Старт 100/12, Бизнес 150/25, Корпоратив 400/50). Доп. агенты считаются по 10 200 ₽/мес. Проверено: Бизнес + 2 агента = 45 400 ₽/мес. Попытка менеджера поставить свою цену возвращает ошибку. Ручной прайс — только у админа, через флаг `custom_pricing`.

**Статус нельзя сохранить без даты следующего действия.** Исключения: `new` (холодный пул, ещё не в работе), `won`, `lost`.

**Отказ нельзя сохранить без причины.** Причина — из закрытого списка: `price`, `no_need`, `has_solution`, `unreachable`, `not_target`, `other`.

**Пять недозвонов подряд — автоматический отказ** с причиной `unreachable`. Успешный дозвон сбрасывает счётчик в ноль.

**Каждая смена статуса сама пишется в журнал.** Даже если это сделали напрямую в базе, минуя интерфейс.

**Журнал касаний неизменяем.** Ни менеджер, ни админ не могут отредактировать или удалить запись. Защита стоит в двух слоях: политики RLS и триггер.

**У компании не может быть двух открытых сделок.** Закрытые сохраняются — если вернуться к отказнику через год, старая история отказа останется на месте.

**Представления не обходят защиту.** Все пять созданы с `security_invoker = true`, то есть выполняются с правами того, кто спрашивает. Без этого обычное представление в Postgres работает от имени владельца и открывает данные в обход политик.

**Публичный ключ сам по себе не даёт доступа.** Все политики требуют не просто авторизации, а наличия записи в `profiles`, которую создаёшь только ты вручную. Проверено: пользователь с действующим аккаунтом, но без профиля видит 0 лидов, 0 компаний, 0 касаний, 0 тарифов, и 0 через все представления тоже. Создать ничего не может. Именно поэтому ключ можно спокойно держать в публичном репозитории.

**Удаление — только админ.** Проверено: менеджер удаляет 0 строк, админ удаляет.

**Скоринг обзвона** считается на лету, 0–11 баллов: онлайн-заказ на сайте +3 (интеграция дешевле), своё приложение +2, три и больше точек +2, средний чек от 300 +1, партнёрский канал +2, есть Instagram +1.

Текущий топ по твоей базе: Drinks (5), Bappa (4), Ilis (3), WaySushi (3).

## Что я поправил в данных при импорте

- **Телефоны** приведены к формату `+7XXXXXXXXXX`. В таблице было три разных написания, а у MAXX ROYAL номер был набран математическим жирным юникодом — в таком виде `tel:` на телефоне не сработал бы вообще.
- **Точка** — в колонке Instagram стояла ссылка на 2ГИС. Убрал, вместо неё задача в поле `todo`: найти аккаунт.
- **Wayset** помечен как `kind = 'channel'`, а не лид. Это партнёрский канал к пулу заведений, у него другая логика работы и другой скрипт разговора.
- **SHOKUNIN** — задача про ненайденную карточку 2ГИС перенесена из заметки в `todo`.
- Из заметок вынесены в поля: адреса (8 компаний), число точек, средний чек, наличие сайта с онлайн-заказом и своего приложения, юрлица и ОГРН. Сами заметки сохранены дословно, ничего не потеряно.

## Если понадобится добавить лидов из Excel

`make_seed.py` перегенерирует импорт из обновлённой таблицы. Повторный запуск не создаёт дублей — существующие компании пропускаются.

Пришли Project URL и anon key — соберу `index.html`: четыре экрана, установка на телефон как приложение.

# Как импортировать лидов из таблицы

«Ещё» → «Загрузить лиды из таблицы». Экран виден только администратору.

## Порядок

1. В своей таблице выдели нужные строки **вместе со строкой заголовков** и скопируй.
2. Вставь в поле на экране импорта.
3. Нажми **«Разобрать»**. Появятся предупреждения и превью.
4. Сверь предупреждения. Если что-то не так — правь таблицу и разбирай заново.
5. Нажми зелёную **«Загрузить N в CRM»**. Пока не нажмёшь — в базе ничего не появится.

## Что попадает в поля

Колонки ищутся по названию, **порядок не важен**. Понимаются такие варианты:

| Поле | Подходящие названия колонки |
|---|---|
| Название | Компания, Название, Заведение, Фирма, Company, Name |
| Сегмент | Сегмент, Ниша, Рубрика, Категория, Segment |
| Телефон | Телефон, Тел., Номер, Phone |
| Instagram | Instagram, Инстаграм, Insta |
| 2ГИС | 2ГИС, ГИС, 2gis |
| Заметка | Заметка, Комментарий, Примечание, Описание, Note |

Колонка с названием обязательна, без неё импорт откажется работать. Остальные не обязательны.

**Все прочие колонки дописываются в заметку** в виде «Заголовок: значение». Так ничего не теряется: приоритет, число подписчиков, наличие WhatsApp — всё окажется в заметке лида.

## Что происходит автоматически

- **Телефоны приводятся к единому виду.** Понимает `8 928…`, `+7 928…`, `79281112233`, `9281112233`, номер с текстом вокруг и даже набранный необычным шрифтом.
- **Несколько номеров в одной ячейке** — первый идёт в контакт, остальные в заметку строкой «Ещё телефон». То же с добавочными.
- **Число точек вытаскивается из заметки**, если оно там названо: «11 филиалов», «Минимум 3 точки», «Две точки». Это важно — от числа точек считается приоритет обзвона.
- **Повторные строки заголовков посреди таблицы пропускаются.**
- **Пустые строки пропускаются**, лишние пробелы обрезаются.
- **Повторный импорт дозаполняет, а не дублирует.** Совпадение ищется по названию без учёта регистра.

## Что отбрасывается и почему

- **Ссылки 2ГИС на поиск** (`/search/…`) вместо карточки фирмы (`/firm/…`). По такой ссылке менеджер попадёт в общий поиск, а не в заведение. В превью будет сказано, сколько таких.
- **Ссылки в колонке Instagram, не содержащие `instagram.com`.** Бывает, что туда по ошибке попадает адрес 2ГИС.
- **Неполные телефоны** вида `8 928 735-XX-XX`. Компания загрузится, но без номера — подсветится красным в превью.

## Что нельзя импортировать

**ЛПР** — имя, должность и телефон лица, принимающего решение. Заполняется только вручную в карточке. Это осознанно: на этапе сбора лидов ты ещё не знаешь, кто там решает, это выясняется на первом звонке.

**Статус, тариф, дату следующего шага.** Все загруженные лиды получают статус «Новый» и попадают в холодный пул.

## Повторная загрузка обновлённой таблицы

Это штатный способ работы: собрал названия, потом дозаполнил телефоны, потом Instagram — и каждый раз загружаешь таблицу заново.

Дублей не будет. После «Разобрать» четыре плитки показывают, что произойдёт:

- **новых** — таких компаний в базе нет, создам вместе с лидом
- **дозаполню** — компания есть, но в таблице появилось то, чего в CRM нет
- **без изменений** — всё, что есть в таблице, уже в базе
- **дублей не создам** — всегда ноль

В колонке «Что будет» напротив каждой строки видно точно: «новый», «+телефон, Instagram» или «уже есть».

**Заполненное в CRM не перезаписывается.** Если менеджер поправил телефон вручную, а в таблице другой — останется тот, что в CRM. То же с сегментом, числом точек, ссылками. Импорт только добавляет в пустое.

**Заметки дописываются, а не заменяются.** Если менеджер добавил в заметку «просил перезвонить в среду», а в таблице своя заметка — обе останутся. Повторная загрузка того же текста дубля не создаст.

Если нужно именно перезаписать заполненное — это делается вручную в карточке через «Изменить карточку». Импорт на такое не рассчитан осознанно: иначе одна неосторожная загрузка стёрла бы работу менеджера за неделю.

## Что происходит после загрузки

Лиды создаются **без ответственного** — они в общем пуле. Менеджер видит их в «Лидах» под фильтром «Ничьи» и забирает себе: либо кнопкой «Взять себе», либо просто записав первое касание — тогда лид закрепляется автоматически.

В «Сегодня» они не появятся, пока у них нет даты следующего шага. Это правильно: сначала менеджер разбирает пул, назначает первые звонки, и с этого момента лиды начинают всплывать сами.

## Если что-то пошло не так

Ошибочно загруженное можно удалить: карточка лида → «Удалить лид». Кнопка только у администратора, удаляется вместе с историей.

# Отчёты

Вкладка «Отчёт» в нижнем меню. Три периода: сегодня, 7 дней, 30 дней. Администратор может смотреть по всей команде или по конкретному сотруднику.

## Что считается

- **Касаний** — все записи в журнале за период, кроме системных отметок о смене статуса
- **Дозвон** — доля ответивших от суммы «ответил + не взял». Другие исходы в знаменатель не идут
- **Вышли на ЛПР** — сколько разных лидов, где было отмечено «Говорил с ЛПР»
- **Каналы** — разбивка касаний по звонкам, WhatsApp, Instagram, встречам
- **Движение по воронке** — считается по фактическим сменам статуса за период, а не по текущему состоянию. Лид, прошедший за день бриф и КП, попадёт в обе строки
- **Деньги** — суммы по сделкам, закрытым в статус «Клиент» за период. Плюс отдельно подписка по всему, что сейчас на этапе КП и согласования
- **Почему отказали** — причины по сделкам, ушедшим в отказ за период

## Отправка руководителю

Кнопка «Сохранить картинкой» кладёт PNG в загрузки. Кнопка «Отправить» на телефоне открывает системное меню — можно сразу выбрать WhatsApp или Telegram. Если система такого не умеет, картинка просто сохранится.

Ширина 760 пикселей: в мессенджере читается без открытия на весь экран.

## Отметка «Говорил с ЛПР»

Ставится галочкой при записи касания. Без неё показатель «вышли на ЛПР» останется нулевым — это не поломка, а отсутствие данных.

# Этапы оплаты

Схема одинакова на всех тарифах: **30% предоплата за прототип, 30% за бета-тест, 40% за полную интеграцию.**

Суммы не хранятся, а считаются от суммы внедрения. Поэтому при смене тарифа они пересчитываются сами и не могут разойтись с итогом. Третий этап считается вычитанием первых двух — сумма трёх этапов всегда сходится с итогом до рубля, даже на некруглых числах.

| Тариф | Внедрение | Этап 1 | Этап 2 | Этап 3 |
|---|---|---|---|---|
| Старт | 100 000 ₽ | 30 000 | 30 000 | 40 000 |
| Бизнес | 150 000 ₽ | 45 000 | 45 000 | 60 000 |
| Корпоратив | 400 000 ₽ | 120 000 | 120 000 | 160 000 |

## Как отмечать

В карточке лида блок «Этапы оплаты» с полосой заполнения. Нажатие на этап отмечает его оплаченным, повторное нажатие снимает отметку с подтверждением.

Каждая отметка и каждое снятие попадают в журнал автоматически, на уровне базы. Обойти это через интерфейс невозможно.

Отмечать может и менеджер, и администратор. Задавать свою сумму по-прежнему может только администратор.

## В отчёте

- **Поступило за период** — сумма этапов, отмеченных оплаченными в этом периоде
- **Собрано всего** — сумма всех оплаченных этапов за всё время
