# Внешнее чтение CRM через Composio

Внешние сервисы читают лидов из CRM и не могут ничего изменить. Отказ на запись
даёт сама база, а не приложение: ключ выпущен на роль Postgres `crm_readonly`,
у которой есть только `select`.

Работа CRM не затрагивается. Ключ из `index.html`, вход менеджера, политики
роли `authenticated`, представления и триггеры остаются как были.

## Что уже в репозитории

| | |
|---|---|
| `db/12_readonly.sql` | роль `crm_readonly`, права, политики, функция выпуска ключа |
| `db/17_readonly_full.sql` | остальные таблицы и представления: скрипты, уроки, нормы, показатели |
| `integrations/composio/mcp/index.ts` | MCP-сервер: то, из чего Composio собирает свой коннектор |
| `integrations/composio/crm-readonly.openapi.yaml` | описание той же поверхности в OpenAPI: для прямых запросов и для сверки |
| `integrations/composio/verify.sh` | проверка ключа: пять чтений и шесть попыток записи |

## Шаг 1. Применить миграции

Всё делается в проекте компании: Supabase → проект `wiokdxswbcmjdpalyrat`
(владелец `01balanced@gmail.com`) → SQL Editor → новая вкладка → вставить
`db/12_readonly.sql` целиком → Run.

Файл выполняется одной транзакцией и сам себя проверяет: читает лидов под новой
ролью и пробует записать. Если запись вдруг пройдёт, файл падает и в базе не
остаётся ничего.

В конце выводится контрольная строка. Числа должны быть такими:

| `role_1` | `policies_6` | `selects_7` | `writes_0` |
|---|---|---|---|
| 1 | 6 | 7 | 0 |

Последняя колонка — количество прав на запись у внешней роли. Ноль.

Затем тем же способом `db/17_readonly_full.sql`. Он открывает на чтение
остальное: скрипты и ответы на возражения, уроки и их сдачу, замечания
наставника, нормы и показатели по сотрудникам, ручные цены, приглашения.
Файл тоже сам себя проверяет и падает целиком, если запись вдруг пройдёт.

Его контрольная строка:

| `policies_16` | `selects_24` | `writes_0` |
|---|---|---|
| 16 | 24 | 0 |

**Что уходит наружу после этого файла.** Персональные данные сотрудников:
чья норма и сколько выполнено, кто какой урок сдал и с каким счётом, что
написал наставник, чья почта в приглашении. Это решение владельца: разбор
работы отдела ведётся по всей базе, а не по одним лидам. Прав на запись
по-прежнему нет ни одного.

Вернуть границу к одним лидам, не отзывая ключ:

```sql
revoke select on scripts, lessons, lesson_progress, coaching_notes,
  plan_defaults, ramp_steps, plans, custom_pricing, invites,
  v_today, v_stats, v_plan_today, v_kpi_day, v_kpi_week, v_kpi_month,
  v_team_today from crm_readonly;
```

## Шаг 2. Выпустить ключ

Ключ выпускается внутри проекта компании и наружу не передаётся никаким третьим
сервисом: секрет подписи подставляется в SQL Editor и остаётся в проекте.

1. Supabase → Project Settings → API Keys → JWT Keys → **Legacy JWT Secret**,
   скопировать секрет. Legacy JWT Secret должен оставаться включённым: ключ
   подписывается им.
2. В SQL Editor:

```sql
select crm_readonly_token('<сюда JWT Secret>', 365, 'wiokdxswbcmjdpalyrat');
```

Вернётся строка вида `eyJhbGciOi…` — это и есть ключ. Срок — 365 дней,
второй аргумент можно поменять.

**Сначала убедиться, что секрет тот самый.** Если подписать чужим или
устаревшим значением, база молча отвергнет ключ с `PGRST301`, и понять причину
по ответу невозможно. Проверка занимает один запрос (нужен `db/13_key_check.sql`):

```sql
select jwt_check('<legacy anon key>', '<сюда JWT Secret>');
```

`legacy anon key` — из Project Settings → API Keys, раздел устаревших ключей,
строка `anon`. Это открытый ключ проекта, подписанный тем же секретом.
Ответ `true` означает, что секрет верный и выпущенный им ключ база примет.
Ответ `false` — секрет не тот, ключ выпускать бессмысленно.

Разобрать уже выпущенный ключ, не зная секрета:

```sql
select jwt_header('<ключ>'), jwt_payload('<ключ>');
```

Должны быть `{"alg":"HS256","typ":"JWT"}` и `"role": "crm_readonly"`.

Ключ хранить как пароль. Он даёт чтение всех лидов и телефонов.

Отозвать все выпущенные ключи разом:

```sql
revoke crm_readonly from authenticator;   -- все ключи перестают работать сразу
grant  crm_readonly to authenticator;     -- вернуть доступ
```

## Шаг 3. Поставить MCP-сервер

Свой коннектор в Composio собирается **только из MCP-сервера**: в диалоге
«Add Custom MCP» просят URL сервера, а импорта OpenAPI в дашборде нет. Supabase
отдаёт обычный REST, поэтому между ними ставится тонкая прослойка —
`integrations/composio/mcp/index.ts`.

Своих прав у неё нет ни одного. Ключ приходит от Composio в заголовке
`Authorization` и передаётся в базу как есть: что разрешено ключу, то и
произойдёт. Сервер живёт в том же проекте Supabase, новых поставщиков и
паролей не появляется.

1. Supabase → слева **Edge Functions** → **Deploy a new function** → **Via Editor**.
2. Имя функции: `crm-mcp`.
3. Стереть заготовку и вставить целиком
   [`integrations/composio/mcp/index.ts`](../integrations/composio/mcp/index.ts).
4. **Deploy**.
5. Открыть функцию → её настройки → выключить **Verify JWT** (проверку токена
   самой платформой). Иначе Supabase отобьёт запрос Composio раньше, чем тот
   дойдёт до базы: Composio присылает только `Authorization`, а платформа ждёт
   ещё и `apikey`.

   Открытым доступ от этого не становится: без ключа функция ничего не отдаёт,
   а с ключом отдаёт ровно то, что ключу разрешено. Все проверки — в базе.

**Адрес брать из колонки URL в списке функций, а не собирать из имени.**
Редактор подставляет адрес сам, и он не совпадает с именем: функция может
называться `crm-mcp`, а отвечать по адресу
`https://wiokdxswbcmjdpalyrat.supabase.co/functions/v1/quick-endpoint`.
Рядом с адресом есть кнопка копирования — ей и пользоваться.

Проверить, что сервер поднялся (ключ для этого не нужен, список инструментов
открыт):

```bash
curl -s -X POST '<адрес из колонки URL>' -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Должны прийти тринадцать инструментов. `{"code":"NOT_FOUND"}` означает, что
адрес взят неверно.

## Шаг 4. Собрать коннектор в Composio

Под аккаунтом компании, не под личным.

**Сначала выбрать область.** У Composio их две, и каталоги у них разные:
переключатель **Switch** слева сверху, **FOR YOU** и **PLATFORM**. Коннектор,
созданный в PLATFORM, ИИ-клиенту не виден: PLATFORM — это сборка агентов через
SDK. Нужен **FOR YOU**.

Switch → **FOR YOU** → **Connect Apps** → **Add Custom MCP**. Заполнить:

| Поле | Значение |
|---|---|
| Display name | `Balance CRM (только чтение)` |
| MCP server URL | адрес из колонки URL в списке Edge Functions |
| Authentication | `API key` |
| Header name | `Authorization` |
| Header prefix | `Bearer` |

**Add** → подключить (Connect) → в поле ключа вставить ключ из шага 2.
Подключение должно стать Active.

Готовый коннектор Supabase из каталога Composio **не подходит**: он работает
через управляющий токен аккаунта Supabase, а это полный доступ к проекту.
Нужен свой, с ключом только на чтение.

## Шаг 5. Что читается

Коннектор отдаёт тринадцать инструментов:

| Инструмент | Что делает |
|---|---|
| `list_leads` | лиды целиком: статус, уровень контакта, тариф, суммы, этапы оплаты, заметка, дата заведения. Фильтры по статусу, сегменту, уровню, дате; поиск по названию |
| `get_lead` | один лид целиком |
| `list_activities` | журнал касаний: текст заметки, с кем говорили, какое демо отправлено, какой скрипт и какое возражение применялись, кто автор |
| `list_companies` | заведения |
| `list_tariffs` | тарифы |
| `list_scripts` | скрипты звонков, ответы на возражения, шаблоны сообщений — формулировки целиком |
| `list_lessons` | уроки с текстом и вопросами, кто их сдал |
| `list_team` | сотрудники: план и факт на сегодня, при желании приглашения |
| `list_kpi` | показатели по дням, неделям и месяцам |
| `list_plans` | норма по умолчанию, разгон новичка, персональные планы |
| `list_custom_pricing` | ручные цены мимо прайса |
| `list_coaching_notes` | замечания наставника |
| `check_write_rejected` | пробует создать лид; обязан вернуть 403 и код `42501` |

Наружу отдаётся вся база. Закрытых таблиц не осталось.

**Списки страничные.** У каждого есть `limit` (до 1000) и `offset`, а в ответе
поле `всего`: сколько строк подходит под фильтр целиком. Если `всего` больше,
чем `показано`, забирать остальное следующим вызовом с `offset`.

**Три представления внешнему ключу данных не дадут, и это не поломка.**
`v_today`, `v_stats` и `v_plan_today` показывают дела текущего пользователя,
а у внешнего ключа в токене нет `sub`: он ничей. Те же числа за отдел целиком
дают `list_team` и `list_kpi`.

## Шаг 6. Проверить

В Composio выполнить `list_leads` — вернётся список лидов со статусами и
суммами. Затем `check_write_rejected` — вернётся:

```json
{
  "проверка": "попытка создать лид тем же ключом",
  "код_ответа": 403,
  "ответ_базы": { "code": "42501", "message": "permission denied for table leads" },
  "итог": "запись отклонена, доступ только на чтение"
}
```

Тем же ключом мимо Composio, если есть компьютер с терминалом:

```bash
sh integrations/composio/verify.sh '<ключ>'
```

Шестнадцать чтений и шесть попыток записи (POST, PATCH, DELETE, вставка
в журнал и вызов процедуры `log_touch`). Должно быть «Совпало: 22,
разошлось: 0». Если чтение скриптов или уроков вернуло 403 с кодом `42501`,
не применён `db/17_readonly_full.sql`.

Если хоть одна запись прошла — немедленно `revoke crm_readonly from authenticator;`
и разбираться.

## Почему запись невозможна

Три независимых рубежа. Достаточно любого из них, но стоят все три.

1. **Права.** У роли `crm_readonly` есть только `select` — на 24 объекта
   после файла 17, на 8 до него.
   `insert`, `update`, `delete` не выданы нигде. Postgres отвечает `42501`
   ещё до того, как посмотрит на строки.
2. **Политики RLS.** Для этой роли заведены только политики `for select`.
   Даже если кому-то позже выдадут `grant insert`, вставку отобьёт RLS.
3. **Процедуры.** `log_touch`, `create_lead` и `apply_invites` отобраны у роли
   `public`, у внешнего ключа права на вызов нет. Сами они и так работают
   с правами вызывающего, то есть упёрлись бы в первый рубеж.

Отдельно: сам ключ ничего не даёт без членства `crm_readonly` в `authenticator`.
Один `revoke` закрывает доступ всем выпущенным ключам сразу, менять ничего
больше не нужно.

## Что проверено локально

Postgres 16, вся цепочка `db/00`–`db/17` с нуля, каждый файл дважды.
Все 59 обращений, которые формирует MCP-сервер, выполнены под ролью
`crm_readonly`: каждое представление, каждая колонка в выборке, в фильтре
и в сортировке существует и роли видна.

Файл 12 проверялся отдельно поверх живой PostgREST 12.2.3 с ключом,
выпущенным `crm_readonly_token()`: `initialize`, `tools/list`, инструменты,
пачка сообщений, поток `text/event-stream`, запрос без ключа и с чужим ключом.

- Чтение ключом: `v_leads`, `leads`, `companies`, `contacts`, `activities`,
  `tariffs` — 200.
- После файла 17 читаются и `scripts`, `lessons`, `lesson_progress`,
  `coaching_notes`, `plan_defaults`, `ramp_steps`, `plans`, `custom_pricing`,
  `invites`, `v_team_today`, `v_kpi_day`, `v_kpi_week`, `v_kpi_month`.
- До файла 17 те же объекты отвечали 403 `42501`.
- POST `/leads`, POST `/companies`, PATCH `/leads`, DELETE `/leads`,
  POST `/activities`, POST `/rpc/create_lead`, POST `/rpc/log_touch` — 403 `42501`.
- Менеджер: `v_leads`, `v_today`, `v_stats`, `scripts`, `create_lead`,
  `log_touch`, вставка компании — работают как раньше.
- Админ: ручные цены, приглашения, `apply_invites` — работают как раньше.
- Посторонний с аккаунтом, но без строки в `profiles`: везде нули, вставка
  отбита политикой.
- Аноним с публичным ключом из `index.html`: `permission denied`.
