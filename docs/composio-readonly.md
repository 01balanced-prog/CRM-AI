# Внешнее чтение CRM через Composio

Внешние сервисы читают лидов из CRM и не могут ничего изменить. Отказ на запись
даёт сама база, а не приложение: ключ выпущен на роль Postgres `crm_readonly`,
у которой есть только `select`.

Работа CRM не затрагивается. Ключ из `index.html`, вход менеджера, политики
роли `authenticated`, представления и триггеры остаются как были.

## Что уже в репозитории

| | |
|---|---|
| `db/12_readonly.sql` | роль `crm_readonly`, права, политики, функция выпуска ключа |
| `integrations/composio/crm-readonly.openapi.yaml` | описание коннектора для импорта в Composio |
| `integrations/composio/verify.sh` | проверка ключа: пять чтений и шесть попыток записи |

## Шаг 1. Применить миграцию

Всё делается в проекте компании: Supabase → проект `wiokdxswbcmjdpalyrat`
(владелец `01balanced@gmail.com`) → SQL Editor → новая вкладка → вставить
`db/12_readonly.sql` целиком → Run.

Файл выполняется одной транзакцией и сам себя проверяет: читает лидов под новой
ролью и пробует записать. Если запись вдруг пройдёт, файл падает и в базе не
остаётся ничего.

В конце выводится контрольная строка. Числа должны быть такими:

| `role_1` | `policies_6` | `selects_7` | `writes_0` |
|---|---|---|---|
| 1 | 6 | 7 | 0 |

Последняя колонка — количество прав на запись у внешней роли. Ноль.

## Шаг 2. Выпустить ключ

Ключ выпускается внутри проекта компании и наружу не передаётся никаким третьим
сервисом: секрет подписи подставляется в SQL Editor и остаётся в проекте.

1. Supabase → Project Settings → API Keys → JWT Keys → **Legacy JWT Secret**,
   скопировать секрет. Legacy JWT Secret должен оставаться включённым: ключ
   подписывается им.
2. В SQL Editor:

```sql
select crm_readonly_token('<сюда JWT Secret>', 365, 'wiokdxswbcmjdpalyrat');
```

Вернётся строка вида `eyJhbGciOi…` — это и есть ключ. Срок — 365 дней,
второй аргумент можно поменять.

Ключ хранить как пароль. Он даёт чтение всех лидов и телефонов.

Отозвать все выпущенные ключи разом:

```sql
revoke crm_readonly from authenticator;   -- все ключи перестают работать сразу
grant  crm_readonly to authenticator;     -- вернуть доступ
```

## Шаг 3. Собрать свой коннектор в Composio

Всё под аккаунтом компании в Composio, не под личным.

1. Dashboard → Apps → **Create custom toolkit** (свой коннектор).
2. Способ описания — **OpenAPI**. Загрузить
   `integrations/composio/crm-readonly.openapi.yaml`.
   Название — `Balance CRM (только чтение)`.
3. Аутентификация — **API Key**, два заголовка с одним и тем же значением:

   | Заголовок | Значение |
   |---|---|
   | `apikey` | ключ из шага 2 |
   | `Authorization` | `Bearer ` + ключ из шага 2 |

   Supabase требует оба: первый проходит шлюз, второй определяет роль в базе.
4. Сохранить и подключить (Connect) — появится подключение с этим ключом.

Готовый коннектор Supabase из каталога Composio **не подходит**: он работает
через управляющий токен аккаунта Supabase, а это полный доступ к проекту.
Нужен свой, с ключом только на чтение.

## Шаг 4. Что читается

| Операция | Что отдаёт |
|---|---|
| `listLeads` | лиды карточкой: компания, ЛПР, статус, тариф, суммы, этапы оплаты, следующий шаг, число касаний |
| `listLeadsTable` | таблица `leads` без склейки с компанией |
| `listCompanies` | заведения |
| `listContacts` | контакты: основной номер и ЛПР |
| `listActivities` | журнал касаний |
| `listTariffs` | тарифы |
| `checkWriteRejected` | попытка записи; обязана вернуть 403 |

Фильтры PostgREST: `status=eq.negotiation`, `status=in.(won,lost)`,
`next_action_at=lte.2026-09-30`, `company_name=ilike.*беркат*`.

Наружу **не отдаются**: `custom_pricing` (ручные цены), `invites`, `plans`,
`plan_defaults`, `ramp_steps`, `scripts`, `lessons`, `lesson_progress`,
`coaching_notes`. Это внутренняя кухня отдела и персональные данные сотрудников,
к лидам отношения не имеют.

## Шаг 5. Проверить

Через Composio: выполнить `listLeads` — вернётся список лидов; затем
`checkWriteRejected` — вернётся `403` и
`{"code":"42501","message":"permission denied for table leads"}`.

Тем же ключом с любого компьютера:

```bash
sh integrations/composio/verify.sh '<ключ>'
```

Скрипт делает пять чтений и шесть попыток записи (POST, PATCH, DELETE, вставку
в журнал и вызов процедуры `log_touch`) и печатает итог. Должно быть
«Совпало: 11, разошлось: 0».

Если хоть одна запись прошла — немедленно `revoke crm_readonly from authenticator;`
и разбираться.

## Почему запись невозможна

Три независимых рубежа. Достаточно любого из них, но стоят все три.

1. **Права.** У роли `crm_readonly` есть только `select` на семь объектов.
   `insert`, `update`, `delete` не выданы нигде. Postgres отвечает `42501`
   ещё до того, как посмотрит на строки.
2. **Политики RLS.** Для этой роли заведены только политики `for select`.
   Даже если кому-то позже выдадут `grant insert`, вставку отобьёт RLS.
3. **Процедуры.** `log_touch`, `create_lead` и `apply_invites` отобраны у роли
   `public`, у внешнего ключа права на вызов нет. Сами они и так работают
   с правами вызывающего, то есть упёрлись бы в первый рубеж.

Отдельно: сам ключ ничего не даёт без членства `crm_readonly` в `authenticator`.
Один `revoke` закрывает доступ всем выпущенным ключам сразу, менять ничего
больше не нужно.

## Что проверено локально

Postgres 16, вся цепочка `db/00`–`db/12` с нуля, каждый файл дважды, поверх
живой PostgREST 12.2.3 с ключом, выпущенным `crm_readonly_token()`.

- Чтение ключом: `v_leads`, `leads`, `companies`, `contacts`, `activities`,
  `tariffs` — 200.
- `custom_pricing`, `scripts`, `invites`, `coaching_notes` — 403 `42501`.
- POST `/leads`, POST `/companies`, PATCH `/leads`, DELETE `/leads`,
  POST `/activities`, POST `/rpc/create_lead`, POST `/rpc/log_touch` — 403 `42501`.
- Менеджер: `v_leads`, `v_today`, `v_stats`, `scripts`, `create_lead`,
  `log_touch`, вставка компании — работают как раньше.
- Админ: ручные цены, приглашения, `apply_invites` — работают как раньше.
- Посторонний с аккаунтом, но без строки в `profiles`: везде нули, вставка
  отбита политикой.
- Аноним с публичным ключом из `index.html`: `permission denied`.
