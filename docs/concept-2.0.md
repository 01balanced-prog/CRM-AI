# Balance CRM 2.0: план, скрипты, обучение и кабинет админа

Аудит репозитория на 4 сентября 2026 и концепция развития. Приложение остаётся одним
файлом `index.html`, публикуется перетаскиванием, правила бизнеса живут в базе.

## 1. Что есть сейчас

Один файл, семь экранов: Сегодня, Лиды, карточка, касание, добавление, отчёт-картинка,
импорт. Правила бизнеса в базе: суммы из тарифов, этапы 30/30/40, неизменяемый журнал,
автозакрытие после пяти недозвонов. Две роли уже есть в `profiles.role`, поэтому кабинет
админа не требует новой системы прав, только новых экранов.

## 2. Проблемы

По убыванию важности. Пометка «мешает плану» значит: пока это не исправлено, цифры
плана будут врать.

### Критично

**Папки `db/` нет в репозитории и никогда не было.** README и AGENTS.md ссылаются на
шесть SQL-файлов, в истории git их нет ни в одном коммите. Схема, RLS, триггеры и
представления существуют только внутри Supabase, бэкапов на бесплатном плане нет.
Любая новая миграция должна проверяться всей цепочкой с нуля, а цепочки нет.
Мешает плану: без схемы нельзя написать ни одной миграции. Как выгрузить: `db/README.md`.

**Касание пишется тремя-четырьмя запросами без транзакции.** Порядок: контакт →
запись в `activities` → PATCH лида. Журнал неизменяем, а PATCH может упасть по правилам
базы (нет даты следующего шага, нет причины отказа, триггер пяти недозвонов) или из-за
сети. Касание уже записано, статус не сменился, повторное «Сохранить» даёт дубль.
То же с созданием лида: компания → контакт → лид; если лид не создался, компания
остаётся сиротой, а повтор говорит «Такая компания уже есть». Лечится функциями
`log_touch(...)` и `create_lead(...)` в Postgres, вызов через `rest/v1/rpc`.
Мешает плану: план считает касания, дубли раздуют факт. *Сделано в `db/07_rpc.sql`:
клиент вызывает `log_touch` и `create_lead`, повтор с тем же `client_id` дубль не создаёт.*

### Важно

- **«Записать касание» на третьем экране карточки.** На тестовом лиде карточка заняла
  2,5 высоты экрана. Нужна закреплённая нижняя панель: «позвонить» и «Записать касание».
  *Сделано в нулевом этапе.*
- **Лист касания в два экрана, «Сохранить» на третьем** (1446 px при видимых 742).
  Блок «Узнал контакт» стоит выше комментария и статуса, хотя нужен в одном звонке из
  десяти. Нужно два уровня: исход и дата сверху, остальное под «Подробнее».
  *Сделано в нулевом этапе.*
- **После касания некуда идти.** Четыре действия между звонками. Нужна кнопка
  «Следующий», открывающая очередного из списка на сегодня. *Сделано в нулевом этапе.*
- **Даты считаются в UTC.** `iso()` брал `toISOString()`. С полуночи до трёх ночи по
  Грозному чип «Сегодня» ставил вчерашнюю дату. Представления базы, скорее всего, тоже
  считают `current_date` в UTC. Для дневного плана касание в 23:30 уйдёт в завтра.
  Мешает плану. *Исправлено: клиент считает по местному времени, база по Europe/Moscow.*
- **Без связи касание теряется.** Нужна очередь неотправленных касаний в localStorage
  с повтором. Работает только вместе с RPC и клиентским идентификатором касания.

### Заметно

- Отчёт считается на телефоне из всех лидов и касаний. План и факт для админа и
  менеджера должны считаться в одном месте, в представлениях базы. Мешает плану.
- Людей заводят через SQL Editor, экран «Ещё» менеджера пуст.

### Мелочи

- Поиск подставлял строку в `ilike` без экранирования запятых и скобок PostgREST.
  *Исправлено.*
- `db()` делал `JSON.parse` на любой ответ; HTML-страница ошибки давала «Unexpected
  token». *Исправлено.*
- Параллельные запросы могли одновременно обновлять токен одним refresh_token.
  *Исправлено.*
- `author_id` касания ставит клиент. В базе нужен default через `current_profile_id()`.
  *Сделано в `db/07_rpc.sql`.*
- Мёртвые стили `.dm-who`, `.dm-btns`. *Убраны.*
- «Приоритет N из 13» захардкожен.
- Кнопка «назад» на «Сегодня» никогда не выходит из приложения.
- Все коммиты называются «Add files via upload».
- Версия кэша в `sw.js` поднимается руками. *Теперь версия видна на экране «Ещё».*

## 3. Принципы

1. **Правила живут в базе, интерфейс их показывает.** План, разгон новичка, факт по
   дням считаются в Postgres. Менеджер и админ видят одно и то же число.
2. **Ничего не отвлекает от звонка.** Во время обзвона на экране только кому звонить,
   что сказать, куда записать. План, уроки и замечания показываются до и после.
3. **Контент правится без публикации файла.** Скрипты, возражения, уроки, нормы плана
   хранятся в таблицах. `index.html` обновляется только когда меняется механика.
4. **План это маршрут на день, а не приговор.** Показывает, сколько осталось, хвалит,
   когда закрыл. Рейтинг менеджеров живёт только у админа.

## 4. Устройство по ролям

Одна оболочка, пять вкладок у обеих ролей. Четвёртая зависит от роли.

| | Менеджер | Админ |
|---|---|---|
| 1 | Сегодня + план дня, урок дня, замечания | Сегодня + сводка по команде |
| 2 | Лиды | Лиды |
| 3 | Добавить | Добавить |
| 4 | **Учёба**: скрипты, возражения, уроки | **Команда**: люди, планы, контент, отчёт, импорт |
| 5 | Ещё + отчёт, версия | Ещё |

Отчёт-картинка у менеджера переезжает в «Ещё» и в кнопку внизу «Сегодня». У админа
живёт в «Команде». Админ по-прежнему может вести лидов как менеджер.

## 5. План и разгон новичка

### Метрики

Считаются из того, что уже пишется в журнал. Новых полей менеджеру заполнять не нужно.

| Метрика | Горизонт | Откуда |
|---|---|---|
| `calls` | день | касания с каналом «звонок» и исходом «ответил» или «не взял» |
| `talks` | день | касания с исходом «ответил», любой канал |
| `dm_talks` | день | касания с флагом «говорил с ЛПР» |
| `taken` | день | лиды, у которых в этот день появился ответственный |
| `briefs` | неделя | смены статуса на «Бриф снят» |
| `proposals` | неделя | смены статуса на «КП отправлено» |
| `won`, `cash` | месяц | смены статуса на «Клиент», суммы этапов по датам оплаты |

День считается по `Europe/Moscow` и в базе, и в клиенте.

### Три слоя плана

1. **Нормы по умолчанию** (`plan_defaults`, одна строка): звонки, разговоры, ЛПР в
   день; брифы, КП в неделю; сделки, деньги в месяц.
2. **Разгон** (`ramp_steps`): процент по номеру недели с `profiles.started_at`.
   По умолчанию 40 / 60 / 80 / 100. Отключается для человека галочкой `ramp_enabled`.
3. **Личный план** (`plans`): админ задал человеку на месяц свои цифры. Тогда нормы и
   разгон не участвуют.

Функция `effective_plan(profile_id, day)` возвращает одну строку с нормами на этот
день. Итоговые цифры округляются вверх до целого. Все экраны спрашивают только её.

### У менеджера

Блок «План на сегодня» на экране «Сегодня» над списком звонков. Полоска на метрику,
справа факт/план моноширинным. Выполненная метрика зеленеет и получает галочку.
Тонкая засечка «ожидаемо к этому часу» подсказывает темп. Внизу строка про месяц.
Отчёт-картинка получает строку «План: звонки 24/24, разговоры 8/8, ЛПР 3/2».

## 6. Скрипты и режим звонка

Скрипт привязан к этапу: первый звонок, обход администратора, снятие брифа, звонок
после КП, дожим, возврат после недозвона. Отдельный тип «возражение»: реплика клиента и
ответ. Скрипт может быть привязан к сегменту. Подстановки: `{компания}`, `{лпр}`,
`{тариф}`, `{внедрение}`, `{подписка}`. Форматирование строчное: пустая строка делит
абзацы, `-` пункт, `**жирный**`. Без библиотек.

Режим звонка: в карточке закреплённая нижняя панель (позвонить, Записать касание).
По чипу «Скрипт» выезжает лист со скриптом текущего этапа и чипами возражений.
Лист касания в два уровня. После сохранения «Записано · Следующий →».
В касание пишется, какой скрипт был открыт и какое возражение выбрано.

## 7. Обучение и наставник

Урок: страница текста от админа с 3–5 вопросами. Модули: Продукт, Продажи, CRM.
У урока есть «пройти до конца N-й недели», так программа сшивается с разгоном.
На «Сегодня» у новичка блок «Урок дня». Тест не экзамен: неправильный ответ показывает
правильный и абзац из урока.

Замечания наставника: админ на любом касании оставляет замечание в отдельной таблице
`coaching_notes`. Журнал остаётся неизменяемым. Менеджер видит на «Сегодня»
«Наставник: 1 замечание», читает, отмечает «понял». Причины отказов и выбранные
возражения подсказывают админу, чего в скриптах не хватает.

## 8. Кабинет админа

- **Люди.** Список с фактом дня. Карточка: дата выхода, разгон, личный план, прогресс по
  урокам, последние касания с кнопкой «Замечание», «Отключить доступ» (флаг `active`,
  который проверяет `is_staff()`; история переживает увольнение).
- **Приглашения вместо SQL Editor.** Админ вводит почту, имя, роль → `invites`.
  Регистрация по почте включается, триггер на `auth.users` создаёт профиль только тому,
  чья почта есть в приглашениях. Роль правится только админом (RLS).
- **Нормы плана и разгон.** Один экран, превью «Новичок на 1-й неделе получит: …».
- **Скрипты и уроки.** Списки с переключателем «активен», редактирование с телефона.
- **Отчёт, импорт, выгрузка.** Переезжают сюда. Напоминание первого числа: «Сделай
  выгрузку в Excel».

## 9. Данные

Только дописывающие миграции. Каждая таблица с RLS, `grant` для `authenticated`,
представления с `security_invoker = true`.

| Объект | Что хранит | Кто пишет |
|---|---|---|
| `profiles` + | `started_at`, `active`, `ramp_enabled` через `add column if not exists` | админ |
| `invites` | почта, имя, роль, кто пригласил, когда использовано; триггер на `auth.users` | админ |
| `plan_defaults` | одна строка норм дня, недели, месяца | админ |
| `ramp_steps` | номер недели → процент | админ |
| `plans` | личный план: сотрудник, месяц, семь цифр, кто задал | админ |
| `effective_plan()` | план сотрудника на дату с учётом трёх слоёв | читают все |
| `v_kpi_day`, `v_kpi_week`, `v_kpi_month` | факт по сотруднику и периоду, день по Europe/Moscow | читают все |
| `v_plan_today` | план и факт текущего пользователя одной строкой | свой |
| `scripts` | тип, этап, сегмент, заголовок, текст, порядок, активен | админ |
| `lessons` | модуль, заголовок, текст, вопросы jsonb, порядок, «до недели» | админ |
| `lesson_progress` | сотрудник, урок, когда пройден, результат; уникальная пара | свой |
| `coaching_notes` | от кого, кому, к какому касанию, текст, когда прочитано | админ / менеджер отмечает |
| `activities` + | `client_id uuid unique` от дублей; `script_id`, `objection_id` | через `log_touch` |
| `log_touch()`, `create_lead()` | касание с контактом и статусом одной транзакцией; компания, контакт, лид одной транзакцией | все |

Ни одно из существующих бизнес-правил не ослабляется.

## 10. Порядок внедрения

Каждый этап это законченная задача для Claude Code, после которой файл можно выкладывать.

0. **Фундамент.** Схема в `db/00_baseline.sql`. Функции `log_touch`, `create_lead`,
   перевод на них листа касания, добавления лида, импорта. День по Europe/Moscow.
   Закреплённая панель карточки, двухуровневый лист касания, «Следующий».
   Файлы: `db/00_baseline.sql`, `db/07_rpc.sql`, `index.html`, `sw.js`.
   *Сделано. Схема восстановлена по клиенту, не выгружена: как сверить, в `db/README.md`.*
1. **Команда и приглашения.** Колонки в `profiles`, `invites`, триггер регистрации,
   вкладка «Команда», карточка сотрудника, отключение доступа. `db/08_team.sql`.
2. **План и разгон.** Нормы, ступени, личные планы, функция плана, представления
   факта, блок плана на «Сегодня», экран норм, строка плана в отчёте. `db/09_plans.sql`.
3. **Скрипты и режим звонка.** Таблица, редактор, лист скрипта с подстановками, чипы
   возражений, вкладка «Учёба». `db/10_scripts.sql`.
4. **Обучение и наставник.** Уроки, прогресс, «урок дня», замечания к касаниям.
   `db/11_lessons.sql`.
5. **Полировка.** Очередь без связи, засечка темпа, серия дней, напоминание о выгрузке,
   мелочи из списка проблем.

### Чего сознательно не делаем

- Push-уведомления: нужен сервер с ключами VAPID. Напоминания внутри приложения.
- Публичный рейтинг менеджеров: только у админа.
- Запись звонков: телефон не отдаёт аудио звонка веб-приложению.
- Сборка, модули, фреймворки: файл остаётся одним.
